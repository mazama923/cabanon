# Data model

This is the intended relational model. It is a design contract, not yet a migration. All monetary values are signed integer cents with an ISO 4217 currency code. The initial release should support one currency per household.

## Household budgeting

| Entity | Important fields | Notes |
| --- | --- | --- |
| `households` | `id`, `name`, `currency`, `created_at` | Tenant boundary for every financial record |
| `users` | `id`, `email`, `password_hash`, `created_at` | One authenticated identity per person |
| `residents` | `id`, `household_id`, `user_id`, `display_name`, `active_from`, `active_until` | A contribution is calculated over active residents for a period |
| `expense_categories` | `id`, `household_id`, `name`, `kind` | Examples: groceries, utilities, rent, insurance |
| `expenses` | `id`, `household_id`, `category_id`, `amount_cents`, `incurred_on`, `description`, `created_by` | Immutable financial amount after confirmation; corrections use a reversal |
| `expense_splits` | `expense_id`, `resident_id`, `amount_cents` | Persist the calculated split so historical results remain reproducible |
| `payments` | `id`, `resident_id`, `amount_cents`, `paid_on`, `reference` | Record transfers to the joint account |

`expense_splits.amount_cents` must sum exactly to `expenses.amount_cents`. The domain function exposes the base share and the number of residents who pay one extra cent, avoiding rounding ambiguity.

For contribution planning, `plan_contributions` applies the available account balance to expenses first, up to the expense total. Contributions are calculated from the remaining amount and never become negative; any surplus balance is returned separately. The current browser client takes this balance as an in-memory input. Whether it should later be derived from persisted account activity belongs to the persistence design.

## Construction cost history

The current browser screen records actual costs only. Each entry has a date, description, category, and non-negative integer-cent amount. Record an invoice or purchase once; do not create duplicate entries for its instalments. The client shows the total and subtotals by category. Entries and custom categories currently exist only in browser memory and are cleared when the page reloads.

| Entity | Important fields | Notes |
| --- | --- | --- |
| `construction_projects` | `id`, `household_id`, `name`, `starts_on` | A household can retain historical projects |
| `construction_categories` | `id`, `project_id`, `name`, `sort_order` | User-defined categories, initially construction, interior, and exterior |
| `construction_costs` | `id`, `project_id`, `category_id`, `actual_cents`, `incurred_on`, `description` | One confirmed invoice or purchase; amount stored in integer cents |

PostgreSQL persistence, correction/reversal workflows, and any estimate or forecast feature are future work. Financial history must not be silently deleted when those workflows are implemented.

## Integrity rules

- Use UUID primary keys generated by PostgreSQL.
- Add `household_id` directly to tables that are frequently filtered by household, even where derivable; enforce it with foreign keys and indexes.
- Use `NOT NULL`, `CHECK (amount_cents >= 0)`, and foreign keys as close to the data as possible.
- Do not use `ON DELETE CASCADE` for financial records. Deactivate records or create explicit reversals.
- Add `created_at`, `updated_at`, and `created_by` to user-editable records.
- Keep uploaded invoices outside PostgreSQL if added later; store encrypted object metadata and a content hash in the database.
